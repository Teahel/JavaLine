# 设备查询规则与验证

`GET /trino/devices` 保留原分页参数与返回字段，按设备主表行分页。

## 查询流程

1. COUNT 仅查询 `project_device`，存在关联筛选时才追加 EXISTS。展示字段不参与计数。
2. 使用相同条件查询当前页设备，按创建时间、项目编码和设备编码依次倒序排序。
3. 将当前页标识作为参数化 VALUES 传给详情查询。图片、系统、生产、发货、上报信息均限定在当前页设备范围内，并在关联前收敛到每个关联键最多一条。

空结果或超出总数的页只执行 COUNT。非空页固定执行三条 SQL，不逐台查询。Trino 会内联 CTE，因此详情查询传入的是已经查出的页标识，而非反复引用原分页 SQL。

## 业务规则

- 图片按 upload_time 倒序取一条，空时间排最后。同一时间按图片 URL、地址、经纬度倒序决定展示内容；所有返回字段相同的重复行不影响结果。
- 业务系统名称去重、排序后以 `, ` 拼接，保留 `system_name` 字符串类型。筛选某个系统时仍展示设备全部系统。
- 发货按 delivery_task.create_time 倒序取一条，时间相同按单号倒序，再按客户、备注排序。客户、单号、时间条件均在选出最新发货记录之后应用。只有旧记录匹配的设备不会返回。
- 生产条件保持“任意关联生产记录匹配”的语义。若存在多条匹配记录，展示其中创建时间最新的一条，时间相同按生产编号倒序；无生产条件时展示最新关联生产记录。
- 各时间范围均为左闭右开。
- 同一项目、设备、来源存在多条上报记录时取 MAX；保留原先集中器优先、仪表兜底的 COALESCE 逻辑。
- 发货按设备编码直接关联发货明细，不要求先存在 device_info 记录。

## 数据约束与限制

仓库未包含数据库 DDL。实现沿用现有设备关联键，要求 project_device 的 `(project_code, dev_num)` 唯一，项目表同一 project_code 对应同一项目名称。设备编码用于图片、业务系统和生产发货关联，这些关联表不能区分同编号的不同物理设备。部署前应确认这些约束；主表本身重复时需清理或依据真实主键重新定义设备身份，不能靠末尾 DISTINCT 掩盖。

分页仍支持 pageNum/pageSize，没有改成游标。深分页仍有 OFFSET 成本。COUNT、分页、详情是独立查询，源数据并发变化时不提供跨数据源快照一致性。

存在发货条件时需要先计算最新发货记录，这仍可能扫描较多历史数据。实际效果取决于源库索引、数据量和 connector 下推情况，不能仅按 SQL 数量判断性能。

## 验证

使用项目要求的 Java 17 或更新 JDK：

```sh
mvn -Dtest=TrinoQueryServiceImplTest test
```

测试在 H2 内存库执行实际生成的 SQL，通过适配层替换 catalog 前缀、分页语法以及数组展示函数。覆盖一对多数据不放大行数、最新图片、系统合并、先取最新发货再筛选、时间边界、参数绑定和分页。它验证关系语义，不能代替真实 Trino 的语法、类型、下推和性能验证。

连接测试环境后，应分别对无条件、设备编号、业务系统、最新客户和发货时间筛选的 COUNT / 分页 / 详情 SQL 检查 EXPLAIN，并对比完整接口耗时、扫描行数、网络传输量和返回结果。重点确认设备关联字段及发货设备编号、发货单号、创建时间的源库访问计划。
